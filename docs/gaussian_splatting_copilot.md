# Gaussian Splatting in Mobi-Pi

## Executive summary

Mobi-Pi uses 3D Gaussian Splatting (3DGS) as a learned, view-dependent scene renderer for simulated RoboCasa kitchens. The splat is not the navigation policy and it is not used to control the robot directly. Its job is to answer a visual question for many hypothetical robot base poses:

> If the robot were placed at `(x, y, yaw)`, what would each of its manipulation-policy cameras see?

The answer is generated by rendering a pre-trained Nerfstudio `splatfacto-big` checkpoint from camera poses synthesized for that hypothetical base pose. The rendered views are compared with camera images from the manipulation-policy demonstrations. A Bayesian optimizer then selects the base pose whose rendered views are most in-distribution, subject to visibility, field-of-view, and collision constraints.

This repository contains the dataset-generation and inference glue, but delegates the actual Gaussian parameter optimization and rasterization to Nerfstudio/gsplat. In other words, Mobi-Pi trains and consumes 3DGS models; it does not implement the 3DGS optimizer itself.

## Where the implementation lives

- [collect_images.py](../mobipi/scene_model/collect_images.py) creates simulated RGB/depth views, a point-cloud initialization, `transforms.json`, and launches Nerfstudio training.
- [scene_model.py](../mobipi/scene_model/scene_model.py) loads a Nerfstudio checkpoint and renders RGB images from arbitrary camera extrinsics.
- [download_scene_models.py](../mobipi/scripts/download_scene_models.py) downloads pre-trained scene-model archives from the project server.
- [eval_mobipi.py](../mobipi/eval/eval_mobipi.py) connects rendering to candidate-pose scoring and Bayesian optimization.
- [score_utils.py](../mobipi/utils/score_utils.py) combines collision, object-detection, and image-identity scores.
- [env_utils.py](../mobipi/utils/env_utils.py) defines camera intrinsics, camera-to-world extrinsics, and the conversion from a robot base pose to camera poses.
- [README.md](../README.md) documents the intended download and training workflows.

## Model lifecycle

### 1. Select a simulated scene

Each model is associated with a task/environment and a RoboCasa layout/style pair. The default benchmark split is:

- Training layouts: `0, 2, 3, 5, 6`
- Test layouts: `1, 4, 7, 8, 9`

The scene model is intended to represent the static kitchen scene, not a moving robot or a task episode. During data collection the robot is not placed in the environment (`place_robot=False`), and robot geometry is hidden before rendering.

### 2. Generate training views

The command-line entry point is the `main` function in [collect_images.py](../mobipi/scene_model/collect_images.py). For each sampled view it:

1. Samples a collision-free `(x, y)` position inside the floor polygon and away from fixture polygons.
2. Uses four camera heights and corresponding downward pitch angles: heights `3.0, 2.1, 1.2, 0.3`, with pitches `60, 75, 105, 120` degrees.
3. Samples a random camera heading.
4. Moves the MuJoCo `freeview` camera, renders RGB plus depth, flips the simulator output vertically, and saves `frame_####.png`.
5. Records the camera position, camera rotation matrix, and field of view.
6. Back-projects valid depth pixels into world coordinates and associates each point with its RGB value.

The default is `1000` views, implemented as `250` sampled planar positions times four camera elevations. Each view contributes up to `8192` sampled RGB-D points to a combined point cloud. The combined cloud is written as `pc.ply`; Open3D voxel-downsamples it with voxel size `0.02` if it exceeds the requested point count.

### 3. Build the Nerfstudio dataset description

`save_nerfstudio_data` writes `transforms.json` containing:

- `camera_model: "OPENCV"`
- focal lengths `fl_x`, `fl_y`, derived from the average vertical field of view
- principal point at the image center (`cx`, `cy`)
- image dimensions (`w`, `h`)
- a relative `file_path` for every saved image
- one 4x4 camera transform per image
- `ply_file_path` pointing at `pc.ply`

The transform is assembled as a camera pose with the recorded camera rotation in the upper-left 3x3 block and camera position in the translation column. The camera convention is corrected in [env_utils.py](../mobipi/utils/env_utils.py) by multiplying the MuJoCo pose by a diagonal correction that flips the camera Y and Z axes. This is important: the stored poses are intended to be camera-to-world transforms compatible with Nerfstudio, not raw MuJoCo camera matrices.

### 4. Train with Nerfstudio

After writing the dataset, `collect_images.py` executes:

```bash
ns-train splatfacto-big \
  --data <scene_data_dir> \
  --max-num-iterations 30000 \
  --output-dir <scene_data_dir>/model \
  --viewer.quit-on-train-completion True \
  --pipeline.model.background_color white
```

The repository pins `nerfstudio==1.1.5` in [install.sh](../install.sh). Nerfstudio's `splatfacto-big` pipeline owns the Gaussian representation, densification/pruning, optimization, and CUDA rasterization through its dependencies. The generated model directory is expected to contain a `config.yml`, `dataparser_transforms.json`, and a checkpoint under a path like:

```text
<scene_model_root>/close_drawer/layout1_style1/
  model/splatfacto/<run>/nerfstudio_models/step-000029999.ckpt
```

The configured root is `SCENE_MODEL_ROOT_DIR` in [macros.py](../mobipi/macros.py), optionally overridden by [macros_private.py](../mobipi/macros_private.py). The download script retrieves archives named like `close_drawer_layout1_style1.zip` and extracts them beneath that root.

## Runtime rendering

### Checkpoint loading

`SceneModel.__init__` calls Nerfstudio `eval_setup` using `<checkpoint_dir>/config.yml`. It takes the resulting pipeline model, loads `dataparser_transforms.json`, and stores the caller-provided camera intrinsics. The evaluation code selects the checkpoint by globbing for the requested step, defaulting to step `29999`.

The model's saved dataparser transform and scale are applied to incoming camera extrinsics before rendering:

```text
model_extrinsics = data_transform @ robot_camera_extrinsics * data_scale
```

This is the bridge between RoboCasa world coordinates and the normalized/scaled coordinate system used by the trained Nerfstudio model. Omitting it would put the query camera in the wrong scene coordinate system.

### Perspective render

`SceneModel.render` receives one or more 4x4 camera-to-world matrices. It scales the caller's camera intrinsics to the requested output width, constructs Nerfstudio `Cameras` with `CameraType.PERSPECTIVE`, and calls:

```python
model_outputs = self.model.get_outputs(camera)
rgb = model_outputs["rgb"]
```

The result is an RGB tensor. Evaluation requests `224 x 224` images because the downstream scoring code and the DINO dense-descriptor path are checked for that size.

### Batch wrapper

`BatchSceneModel` creates one `SceneModel` per policy camera and exposes `render(extrinsics_list)`. Despite the name and the presence of a thread helper, the active `render` method loops sequentially over the camera models and stacks the outputs. It is a multi-camera wrapper, not a vectorized multi-pose renderer.

### Top-down rendering

`SceneModel.render_topdown` also constructs a Nerfstudio orthographic camera. It places the camera above a requested XY center, points it downward, and renders an RGB map. The current evaluation path does not use this method for pose scoring; top-down visualizations generally use a direct MuJoCo camera instead. The method should therefore be treated as an auxiliary/debug path, and its hard-coded height and coordinate assumptions should be checked before relying on it for metric generation.

## How a candidate robot pose becomes a rendered view

The evaluated pose is an SE(2) vector:

```text
robot_pose = [x, y, yaw]
```

At environment reset, [eval_mobipi.py](../mobipi/eval/eval_mobipi.py) captures each policy camera's relative position and orientation with `render_image_with_robot_mask`. For a candidate pose, `compute_camera_extrinsics` in [env_utils.py](../mobipi/utils/env_utils.py) then:

1. Builds a Z-axis robot-base rotation from `yaw`.
2. Rotates the camera's base-relative translation into world coordinates.
3. Adds the candidate base XY translation.
4. Rotates the relative camera orientation into world coordinates.
5. Places both in a 4x4 camera-to-world matrix.

For each candidate, those matrices are passed to `BatchSceneModel`. The resulting splat render contains the static scene. The actual robot camera image and robot segmentation mask are then composited over it:

```text
edited = splat_rgb * (1 - robot_mask) + current_robot_rgb * robot_mask
```

This prevents the scene model from needing to reconstruct the robot and preserves the robot appearance used by the manipulation policy. Object detection can be configured to inspect either the splat-only render or this robot-composited render.

## How rendered images affect pose selection

The `HybridDistribution` in [score_utils.py](../mobipi/utils/score_utils.py) evaluates each candidate in stages:

1. **Point-cloud vacancy / collision filter.** The saved `pc.ply` is used by `PCVacancyDistribution` to reject poses that overlap scene geometry or violate workspace boundaries. These candidates receive score `-2`.
2. **Field-of-view filter.** Mobi-Pi requires the candidate target direction to lie within 75 degrees of the current base heading. These candidates receive score `-3`.
3. **Object detection.** The default `MiniCPM-V-2` detector checks whether the task object is visible. Failed candidates receive score `-1`.
4. **Image identity.** DINO dense descriptors are computed for surviving splat renders. Candidate descriptors are compared with descriptors from the first observation images in the manipulation demonstrations. Per-view similarity is matched against training images, the top `k` training neighbors are selected, and their mean cosine similarity is the positive score.

With multiple policy cameras, the score is computed per observation key and the best valid view score is retained. The splat is therefore a differentiable-looking visual lookup mechanism from the optimizer's perspective, but the optimizer itself is black-box Bayesian optimization; no gradient is propagated through the renderer.

`optimize_pose_batch` in [opt_utils.py](../mobipi/utils/opt_utils.py) normalizes the three pose dimensions to `[0, 1]`, samples batches of candidates, asks `scikit-optimize` for new points using the configured acquisition function, and minimizes the negative score. In the default Mobi-Pi run it uses five candidates per batch and records rendered images and scores for later plots.

## Separate uses of the PLY point cloud

The `pc.ply` generated alongside the splat is not the Gaussian model itself. It is a conventional colored point cloud used for geometric vacancy/collision checks. Both the Mobi-Pi evaluator and the collision-aware baseline load it from three directories above the Nerfstudio checkpoint directory. The Gaussian checkpoint provides photorealistic view synthesis; the PLY provides a simpler explicit geometry proxy.

## Downloaded models versus local training

There are two supported workflows:

- **Download:** run [download_scene_models.py](../mobipi/scripts/download_scene_models.py), select tasks and layout/style IDs, and extract the project-provided archives.
- **Train locally:** run `collect_images_batch.py` or `collect_images.py`, generate RGB-D views and `pc.ply`, then let the script invoke Nerfstudio training. Move the resulting scene directories under `SCENE_MODEL_ROOT_DIR` if a custom output directory was used.

The expected naming convention is `<environment snake case>/layout<id>_style<id>`. Evaluation assumes layout and style IDs are usually equal, although the directory lookup can represent other combinations if corresponding models exist.

## Important implementation details and caveats

- **Static-scene assumption:** training hides the robot and captures a reset kitchen. Dynamic task objects, doors, drawers, and robot geometry are not represented as an episode-specific dynamic reconstruction.
- **Coordinate-system sensitivity:** camera rotations are corrected during data collection, then Nerfstudio's dataparser transform and scale are applied again at inference. Changes to either side require validating a rendered camera pose visually.
- **Camera calibration:** training derives one average focal length from the collected `fovy`, while evaluation supplies camera intrinsics obtained directly from the current MuJoCo camera. The image width and height are rescaled to the requested render size.
- **Inference device:** `SceneModel.render_topdown` explicitly selects CUDA when available, while perspective rendering follows the input extrinsics device. The normal Mobi-Pi evaluation path constructs tensors on CUDA.
- **No pose batching in the renderer:** candidate poses are rendered lazily one at a time. The optimizer batches score requests, but each candidate still causes separate camera/model work.
- **Checkpoint lookup is strict:** the default step is `29999`, and a missing or differently named checkpoint causes the glob result to be empty before model construction.
- **Training command is embedded in Python:** changing iteration count, background color, or Nerfstudio pipeline currently requires editing `collect_images.py` or wrapping it externally.
- **Existing version notes:** the README mentions a `torch==2.1.1` troubleshooting recommendation, while the current install script installs PyTorch `2.2.0`. Nerfstudio/gsplat compatibility should be checked against the actual installed environment.
- **Model initialization point:** `collect_images.py` passes the colored PLY to Nerfstudio as an initialization asset through `transforms.json`; it is later also retained as the collision-checking artifact.

## End-to-end data flow

```text
RoboCasa/MuJoCo kitchen
        |
        | sampled camera poses, RGB, depth
        v
images/ + transforms.json + pc.ply
        |
        | ns-train splatfacto-big, 30,000 iterations
        v
Nerfstudio config.yml + dataparser_transforms.json + step-*.ckpt
        |
        | load checkpoint and apply saved transform/scale
        v
candidate robot pose (x, y, yaw)
        |
        | base-relative policy cameras -> world camera-to-world matrices
        v
3DGS RGB renders at 224x224
        |
        | robot-mask compositing + collision/FOV/object filters
        v
DINO dense-descriptor similarity to policy demonstrations
        |
        | Bayesian optimization over SE(2)
        v
selected navigation pose -> navigate -> run manipulation policy
```
